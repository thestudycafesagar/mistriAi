# Mistri AI Project Architecture & Guidelines

This document provides a comprehensive overview of the **Mistri AI** project (formerly DocExtract AI) to help human developers and AI agents understand the codebase, data flows, and architectural constraints.

## 📌 Project Overview
**Mistri AI** is a Next.js (App Router) web application designed to instantly extract structured tabular data from **Bank Statements, Sales Invoices, and Purchase Invoices** using the **Mistral OCR AI** model. The application features a premium side-by-side UI for verifying original documents against the extracted JSON/Table data, and allows users to export the data directly to CSV for accounting software (e.g., Tally).

## 🛠 Tech Stack & Constraints
- **Framework:** Next.js 14+ (App Router)
- **Language:** TypeScript / React
- **Styling:** Pure CSS Modules (`.module.css`). **STRICT RULE: Do NOT use Tailwind CSS.**
- **AI/OCR Provider:** Mistral AI (`@mistralai/mistralai` SDK) using `mistral-ocr-latest` model.
- **Queueing:** `p-queue` for server-side rate limiting.
- **PDF Manipulation:** `pdf-lib` for in-memory PDF chunking.

## 📂 Project Structure & Key Files

### 1. Frontend Components & Layout
- **`src/app/page.tsx`**: The main orchestrator and state manager. 
  - **State:** Holds the uploaded `file`, selected `activeDocType`, extraction `result`, and an `elapsedTime` stopwatch timer.
  - **Layout Logic:** When no result is present, it shows a centered `<UploadForm />`. Once data is successfully extracted, it switches to a side-by-side layout (Split View), rendering an `<iframe>` / `<img>` preview of the document on the left, and the `<ResultsTable />` on the right.
- **`src/app/layout.tsx`**: The root layout, containing global fonts, metadata, and the basic HTML shell.
- **`src/components/UploadForm/UploadForm.tsx`**: A drag-and-drop file upload component. It validates file types (PDF, JPEG, PNG, etc.), sizes (max 25MB), and makes the `POST` request to `/api/extract` via native `fetch`. It also displays the live extraction timer.
- **`src/components/ResultsTable/ResultsTable.tsx`**: Displays the extracted data. Shows total parse time (`elapsedTime`, passed down from `page.tsx`'s stopwatch) both as a header badge and in the footer. For bank statements, also shows compact "Dr ₹X" / "Cr ₹Y" total badges directly in the top header row (`.headerDebit`/`.headerCredit` in the CSS module) for at-a-glance totals, in addition to the fuller `summaryBar` (totals + reconciliation badge) below the header. Features a segmented tab control to switch between:
  - **Table View:** A sortable, structured grid with an **Export CSV** button.
  - **JSON View:** A syntax-highlighted raw JSON viewer with a **Copy JSON** button.
- **`src/components/StatusBadge/StatusBadge.tsx`**: A small pill badge showing status (Idle, Processing, Error, Success).

### 2. Backend API Routes
Three route files, all thin wrappers around the shared `handleExtractRequest()` in `src/lib/extractHandler.ts` — validation, queueing, retries, and response shape are defined ONCE there and apply identically to all three. A route file only declares which `docType`(s) it accepts and the `maxDuration` route-segment config (which Next.js requires to be a static export in the route file itself, so it can't live in the shared module).

- **`src/app/api/extract/route.ts`**: Generic endpoint used by the web UI (`UploadForm.tsx` posts here). Accepts `docType` as a form field: `BANK_STATEMENT` | `SALES_INVOICE` | `PURCHASE_INVOICE`.
- **`src/app/api/extract/bank-statement/route.ts`**: Dedicated endpoint for external API consumers. No `docType` field needed — always extracts as `BANK_STATEMENT`.
- **`src/app/api/extract/invoice/route.ts`**: Dedicated endpoint for external API consumers extracting invoices. Requires `docType`: `SALES_INVOICE` or `PURCHASE_INVOICE` — both share this one route since they're the same line-item shape with a different ledger direction.
- **`src/lib/extractHandler.ts`**: The actual logic behind all three routes.
  - Validates `file` presence, `docType` (against whichever `allowedDocTypes` the calling route passed in, or skips this check entirely if the route passed a `fixedDocType`), MIME type, and size.
  - Checks `ocrCache` for an exact-duplicate-file hit first; on a miss, enqueues via `enqueueOcr()` (`src/lib/queue.ts`) and stores the result in `ocrCache` after. Returns `{ success, docType, rowCount, columns, data, processingTimeMs, cached }` on success, plus `bankSummary` (see below) when `docType === 'BANK_STATEMENT'`.
  - If the queue is saturated (`QueueSaturatedError`), returns `503` with a `Retry-After` header rather than accepting the request and queueing it anyway — see queue.ts below.
  - Every response — success or error — is plain JSON, so any external caller (not just this repo's frontend) can integrate against these three URLs directly.
  - Every `400` validation failure (missing file, disallowed `docType`, bad MIME type, oversized file) is also logged server-side via `logValidationFailure()` — file name/content-type/size (or `MISSING` if no file was sent) plus every other form field the caller actually sent. Added after a deployed instance returned a `400` to an external caller and there was no way to tell which validation check failed or what the caller actually sent without this; check the server console first when a caller reports an unexplained `400`.
- **`src/app/api/health/route.ts`**: `GET /api/health` — no auth, no file upload, no Mistral call. Reports `200 "ok"` if a Mistral API key is configured (via `hasMistralApiKey()`), `503 "degraded"` if the process is up but not configured to actually extract anything. Response body is currently just `{ status, service }` (simplified by hand from the original design, which also surfaced queue stats and `ledgerMemory` size via `getQueueStats()`/`getLearnedCount()` — those imports are still there if you want to reinstate them). Safe to poll from an uptime monitor.
- **`src/proxy.ts`**: Adds `Access-Control-Allow-Origin: *` (plus `Methods`/`Headers`) to every `/api/*` response, and answers `OPTIONS` preflight requests directly with `204`. Named `proxy.ts` (not `middleware.ts`) and exports a `proxy()` function, not `middleware()` — this Next.js version renamed the file convention; see `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`. Required because external callers (e.g. a separate frontend app on a different origin/IP) hit these routes directly from the browser — without this, the request can succeed server-side and still be blocked client-side by the browser's own CORS check, which looks identical to "the API isn't working" from the caller's side with nothing informative in this app's own logs.
  - **Body-size side effect:** any route a proxy's `matcher` covers gets its request body automatically cloned and buffered by Next.js itself (so both proxy and the route handler can each read it), capped at `proxyClientMaxBodySize` — **10MB by default**, silently truncated with no error to the caller if exceeded. Adding `proxy.ts` with `matcher: '/api/:path*'` therefore caps every upload through this app at 10MB unless overridden — which broke real extractions above ~10MB (the multipart parser correctly found no closing boundary in the truncated body and dropped the file part, logging as "no file field present" with everything empty, easily mistaken for a parser bug). Fixed via `experimental.proxyClientMaxBodySize: '200mb'` in `next.config.ts`, matching `MAX_PDF_SIZE_BYTES` in `extractHandler.ts`. If that PDF cap ever changes, this needs to change with it.

**External API consumers:** see [`API-DOCS.md`](API-DOCS.md) at the repo root — a standalone document (no internal implementation details) meant to be handed directly to third parties who'll call the hosted endpoints. Keep it in sync with `extractHandler.ts` / `schemas.ts` if the request/response shape changes. Note it currently documents these routes as unauthenticated — flag to whoever's distributing the base URL that this means anyone with the link can consume the server owner's Mistral credits.

**Deployment note:** run `next build && next start` (or `npm run build && npm run start`) on a VPS/server, not `next dev`. Dev mode serves extra HMR/dev-only assets and blocks cross-origin requests to them unless the caller's origin is explicitly allowlisted via `allowedDevOrigins` in `next.config.ts` (currently set to `72.61.250.183` as a stopgap) — `next start` doesn't serve those dev-only resources at all, so the restriction (and the warning) doesn't apply in the first place.

### 3. Core Libraries & Logic
- **`src/lib/mistral.ts`**: The core AI engine logic.
  - **Local parser first, for bank statements only (`src/lib/pythonBankParser.ts`):** before any Mistral call, `runOcr()` for `BANK_STATEMENT` PDFs first tries `parse_bank_statement.py` (repo root) as a subprocess — a deterministic, non-AI parser (`pdfplumber` for native/text PDFs, Tesseract OCR via `pdf2image`/`pytesseract` for scanned ones) that costs nothing and is exact when it works. Mistral is only used as a fallback: if the script isn't found, the Python interpreter isn't installed, a required pip package or system dependency (Tesseract/Poppler) is missing, it times out, or it finds zero transactions, `tryPythonBankStatementParse()` returns `null` and `runOcr()` falls straight through to the existing Mistral pipeline below — completely unchanged, same as if this local-parser step didn't exist. This must never be the reason a bank statement extraction fails; every failure mode inside `pythonBankParser.ts` is designed to degrade to `null`, not throw. Scoped to `BANK_STATEMENT` PDFs only — bank-statement images and both invoice types are untouched and always go straight to Mistral.
    - **Column mapping:** the script's JSON output uses whatever header text the source statement itself printed (`"NARRATION"` vs `"PARTICULARS"` vs `"Remarks"` vs `"Transaction"`, `"WITHDRAWAL(DR)"` vs a literal `"Debit"` key, etc.) — not this app's fixed `DATE`/`DESCRIPTION`/`CHEQUE_NO`/`Debit`/`Credit`/`Balance`/`LEDGER` schema. `normalizePythonRow()` in `pythonBankParser.ts` maps between them with keyword heuristics (`date`/`narration`/`particular`/`chq`/`debit`/`withdraw`/`credit`/`deposit`/`balance`), preferring an exact `Debit`/`Credit` key when the script already produced one (it does whenever it detected an inline Cr/Dr marker or a separate Cr/Dr column). `LEDGER` is always left blank by the parser itself; `runOcr()` re-derives it via the same `suggestBankLedger()` used for Mistral-sourced rows, so ledger behavior is identical regardless of which engine produced a row.
      - **Narration keyword matching has a two-tier fallback:** the primary keyword set (`narration`/`particular`/`description`/`detail`/`remark`) is unambiguous, but some banks (e.g. RBL) name their narration column literally `"Transaction"` — matching on bare `transaction` is a weaker signal (it's also a substring of `"Transaction Date"`/`"Transaction Id"`), so it's a second-tier fallback only, and only for a key that isn't itself a date or id column. Confirmed via a real RBL statement where `DESCRIPTION` was coming back empty for every row before this — cross-checked the extracted row count (69) against a raw pdfplumber text dump of the source PDF (69 real date-led lines) to confirm zero data loss, not just "narration is no longer blank."
      - **All keyword matching normalizes away internal whitespace, not just trims ends** (`normalizeKey()`): column headers can carry a stray space mid-word from upstream text extraction, the same class of artifact `ledger.ts` already strips from bank codes (e.g. `"SBIN0002296"` misread as `"S BIN0002296"`). Confirmed on a real ICICI statement whose header came through as `"Withdra wal (Dr)"` — a plain substring check for `"withdraw"` doesn't match text with a space in the middle of the word, so every Debit value was blank. `Deposit (Cr)` had no such gap, so Credit worked fine — same lopsided symptom as the `"Deposits Balance"` and `"Transaction"` cases above. Fixed once, generically, for every keyword check in this file rather than special-cased for ICICI.
    - **Python-sourced rows skip `dedupeBankStatementRows()` entirely** (unlike Mistral-sourced rows, which still go through it). That dedup exists specifically to catch Mistral's chunk-boundary artifacts — the same transaction reported twice by two adjacent 1-page OCR calls. The Python parser does one whole-document pass with no chunks, so there's no boundary-duplication mechanism for it to guard against; running it anyway only risked wrongly deleting a genuine recurring transaction (same date/narration/amount within `DEDUP_WINDOW` (3) rows of another — real statements do contain these, e.g. identical recurring fees or repeated payments to the same party) as if it were a duplicate.
      - **Comma-formatted number strings — the most severe bug found in this whole local-parser feature:** the script only runs its own `clean_numeric()`/`pd.to_numeric()` cleanup on a column whose header matches its fixed `amount_keywords` list — a real header the list doesn't recognize skips that cleanup entirely, leaving raw comma-formatted strings straight from the PDF table (e.g. `"16,000.00"`). `toAmountStr()`/`toBalanceStr()` used to hand that straight to `parseFloat()`, which **silently truncates at the first comma** — `parseFloat("16,000.00")` is `16`, not `16000`; `parseFloat("1,60,000.00")` (Indian lakh-style grouping) is `1`, not `160000` — wrong by 100-1000x with no error thrown. Confirmed on a real Canara statement (1685 rows): the column was named `"WITHDRAWS"`, which the script's keyword list didn't match because it only checked for `"withdrawal"` (requires the "-al"); 198 of 1685 rows (~12%) had their Debit value corrupted this way, and the reported `totalDebit` was off by nearly 13x (₹106,895 vs. the correct ₹1,380,493). Fixed at **both** layers: `parseNumericValue()` in `pythonBankParser.ts` now strips currency symbols, a trailing Dr/Cr suffix, and every comma before parsing (mirrors `clean_numeric()`) regardless of whether the script's own cleanup ran, and the script's `amount_keywords` list now checks for `"withdraw"` (not `"withdrawal"`) so `"WITHDRAWS"`/`"WITHDRAWL"`/etc. are recognized natively too — a strict prefix, so it matches everything the old keyword did plus more, no regression risk. The JS-side fix is the one that actually matters for correctness (it's the defense-in-depth layer that catches *any* future keyword-list gap, not just this one bank's case); the Python-side fix keeps the script's own raw `.xlsx`/`.json` output correct too, for anyone inspecting it directly.
      - **`balance` exclusion is a preference, not a ban, for Debit/Credit matching:** some statements produce a compound header like `"Deposits Balance"` for the actual deposit-AMOUNT column (a header-merge quirk upstream in the script) — a hard ban on any `balance`-containing key blanked every Credit value for a real Canara-format statement (confirmed and fixed). Debit/Credit matching tries a clean non-`balance` key first, then falls back to a `balance`-containing key only if it *also* names a specific amount keyword — a bare `"Balance"`/`"Closing Balance"` column still can never match there.
      - **`Balance` field (added after the above fix, same root cause avoided in reverse):** captures the *per-row running balance* the source statement prints next to each transaction — purely for eyeballing/verifying extraction correctness against the source PDF, distinct from `bankSummary.openingBalance`/`closingBalance` (statement-level, used for reconciliation). Its own key-matching excludes whatever key `Debit`/`Credit` already claimed, so a compound `"Deposits Balance"` column used as Credit is never *also* copied into `Balance` (would silently duplicate the transaction amount as if it were the running total). Uses a separate `toBalanceStr()` (not `toAmountStr()`) because a genuine `0.00` balance is real information and must not collapse to blank the way a `0` Debit/Credit does. Verified against 5 real statements (including the ambiguous `"Deposits Balance"` vs `"Balance"` case) — zero blank `Balance` values, and one statement's real `0.00` balance correctly preserved rather than blanked.
      - **Mistral path:** `bankStatementSchema`'s `transactions` items gained a `Balance` field (`schemas.ts`), and `bankStatementPrompt`'s RULE 3 was rewritten in place — it previously said `"Balance → IGNORE"`, which would have directly contradicted a bolted-on "capture Balance" instruction if added as a separate new rule instead. Never append a rule that tells the model to do something an existing rule already says not to; edit the existing rule.
    - **No reconciliation data:** the script doesn't extract a statement-level opening/closing balance (it actively excludes those lines as non-transactional), so `bankSummary.reconciled` is always `null` (not verified) for a Python-sourced result — same convention as a Mistral chunk that never showed both balances clearly enough to check, never a false `false`.
    - **A trailing "CLOSING BALANCE" row can silently eat the real transaction right before it** in the "standard style" table loop inside `parse_bank_statement.py` (the branch used for statements pdfplumber extracts via explicit gridlines — not the word-coordinate extractor, which already guards against this via `is_divider_or_amount_only_row`). Mechanism, confirmed on a real SBI statement: pdfplumber extracts the statement's trailing `"CLOSING BALANCE  1,616.55CR"` line as its own table row, with a blank date cell. The continuation-merge heuristic (`is_new_txn = bool(clean_row[0]) or non_empty_count >= 3`) misreads that blank-date, 2-cell row as a wrapped continuation of the transaction directly above it and merges `"CLOSING BALANCE"` straight into that transaction's narration — which the `is_balance_marker_row` filter further down (correctly designed to strip genuine standalone closing/opening-balance rows) then matches and deletes **whole**, taking a real transaction down as collateral damage. On that statement, the victim was the very last transaction — a real ₹95 `INTEREST CREDIT` — silently gone, with the extracted `totalCredit` coming up exactly ₹95 short of the statement's own printed total. Fixed by dropping a blank-date row containing a B/F or closing/opening-balance marker phrase *before* the merge step ever sees it (same regex used later by `is_bf_row`/`is_balance_marker_row`, applied one step earlier) — verified the fix recovers all 4 real `INTEREST CREDIT` rows on that statement, and that the extracted `totalDebit`/`totalCredit` now match the statement's own printed "Total Debits"/"Total Credits" line exactly, to the rupee.
    - **`DATE_PAT`/`DATE_RE` only matched purely numeric dates until a real UCO Bank statement (month printed as text, e.g. `"01-Apr-2026"`) broke this catastrophically.** Both regexes required `\d{1,2}[/-]\d{1,2}[/-]\d{2,4}` — a numeric day-month-year triplet — so a month-name date matched **zero** rows as anchors in `extract_transactions_by_word_coords()`. That silently zeroes out `anchor_indices`, which hits `if not anchor_indices: return None, None` and makes the whole (well-designed, already-correct) word-coordinate extractor bail — falling back to the far cruder "standard style" table loop instead, with no error or warning that this happened (confirmed by instrumenting every early-return point in the function; the tell was the absence of the normal `"Word-coordinate extractor found N transactions"` log line). On that fallback path, narration text that wraps *above* its own transaction's date row (this statement's specific layout — the opposite of the "wraps below" layout most other formats use) got glued onto the *wrong* neighboring transaction, corrupting narrations across a run of consecutive rows while leaving amounts correctly positioned — a distinctive symptom (amounts fine, narrations shifted) that pointed straight at a merge/anchor problem rather than a column-mapping one. Fixed by widening the month group in both regexes to accept `\d{1,2}` **or** a 3+ letter month name (`(?:\d{1,2}|[A-Za-z]{3,9})`) — a superset of the old pattern, so every previously-matching numeric date still matches identically. With anchors now correctly detected, the extractor's existing nearest-anchor-by-y-distance merge logic worked correctly with no further changes needed — it was never wrong, it just never got the chance to run. Verified: row count went from 22 (via the broken fallback) to the correct 26, every previously-corrupted narration is now clean, and the extracted totals reconcile exactly against the statement's own printed Opening/Closing Balance (`21609.01 − 21589.00 = −20.01`, matching `0.01 − 20.02 = −20.01` to the paisa). Regression-checked against two numeric-date statements (SBI, Canara) — byte-identical output, confirming the widened pattern changes nothing for dates it already matched.
    - **A trailing "TRANSACTION TOTAL"/"CLOSING BALANCE" row sharing the SAME bordered table as real transactions can silently drop the entire table** — a distinct failure mode from the single-row SBI case above, in the "standard style" continuation-table branch (`h_idx == -1`, used when a later page's table doesn't repeat the header row). Some banks' PDF renderers draw the table border around the trailing summary rows too, so pdfplumber's gridline extraction returns them as the last 1-2 rows of the SAME table object as every real transaction above them, not as a separate standalone box. `is_summary_table()` (designed to detect a genuinely standalone summary box, correctly skipped wholesale) can't tell that apart from this mixed case on phrase content alone — both contain "closing balance" — so it discarded the WHOLE table, taking every real transaction in it down as collateral damage. Confirmed on a real Axis Bank statement: this exact mechanism silently dropped an entire page's worth of 23 real transactions, which looked like "the scanner only reads one page" but was actually this. Fixed with `table_has_dated_row()`: a table is only discarded wholesale if it ALSO has no dated rows of its own — a genuine standalone summary box still has none and is still skipped identically; a mixed table now flows through to per-row processing, where the (widened) blank-date marker-row filter strips just the trailing summary row(s). That filter's phrase list was widened too (added `transaction total`/`total debit`/`total credit`/`grand total`/`sub total`/`carried forward`/`c/f`) since "TRANSACTION TOTAL" doesn't match the SBI fix's original B/F/closing-balance-only phrases — scoped to blank-date rows only (never touches the narration-based, date-agnostic `is_balance_marker_row` DataFrame filter, which was deliberately left unwidened: unlike a blank-date row, that filter has no date guard, so adding "total"-related phrases there risked matching a legitimate transaction whose narration happens to mention one, e.g. a company name). Verified: row count went from 27 (page 1 only) to the correct 50 (27 + page 2's 23), and the extracted `totalDebit`/`totalCredit` match the statement's own printed `TRANSACTION TOTAL` line exactly, to the paisa. Regression-checked against SBI/Canara/UCO — byte-identical output.
    - **`split_crdr_column()` only recognized a direction-indicator column by header name (`"cr/dr"` literally in the column name) — a real PNB statement names it just `"Type"`.** Header: `Date | Amount | Type | Balance | Remarks`, with `Type` holding literal `"CR"`/`"DR"` strings. Since neither `"Amount"` nor `"Type"` matches any Debit/Credit/Withdrawal/Deposit keyword, every row's Debit AND Credit came out blank — no error, just silently empty amounts for the entire statement. Fixed the same way `split_embedded_crdr_amount()` already validates its own guess (by content, not by name): if no column name contains `"cr/dr"`, fall back to checking column *values* — a column where ≥90% of non-blank values are exactly `"CR"`/`"DR"`/`"C"`/`"D"` is the direction indicator regardless of its header text. A real `"Transaction Type"` column (NEFT/UPI/IMPS/Cash) would never pass that value check, so this can't misfire and mistake an unrelated column for the direction indicator. Verified against the real PNB statement (`totalDebit`/`totalCredit` now populate correctly, matching the raw text row-for-row) and regression-checked against Axis/Canara/SBI/UCO — byte-identical output, confirming the name-based path still takes priority when it already works.
    - **Quality gate before accepting a Python-sourced result at all (`pythonBankParser.ts`):** even with every fix above, there will always be some other bank's header-naming variant nobody's hit yet — instead of waiting for the next bug report, `tryPythonBankStatementParse()` now checks its own output before trusting it: if ≥30% of rows (on a statement with ≥5 rows) have BOTH Debit and Credit blank, that's a strong signal the parser found real transaction rows but couldn't identify their amount column at all (exactly the PNB "Type" column failure mode above, before it was fixed). Rather than silently return a statement where every amount is missing, that's treated the same as any other local-parser failure — return `null` and let `runOcr()` fall through to Mistral, which reads the page directly via real OCR instead of depending on column-name pattern matching. Verified this stays silent (accepts the result) on every currently-working statement (PNB/Axis/Canara/SBI/UCO) — it only ever second-guesses a result that's actually broken.
    - **Bare `"DR"`/`"CR"` column headers (no other qualifying word) went unrecognized by both engines — a real Allahabad Bank statement's header was literally `Post Date | Value Date | Description | DR | CR | Balance`.** Python's `amount_keywords` list (`amt`/`amount`/`balance`/`debit`/`credit`/`withdraw`/`deposit`) and JS's `DEBIT_KEYWORDS`/`CREDIT_KEYWORDS` (`debit`/`withdraw`, `credit`/`deposit`) both require one of those words to appear in the header — a two-letter `"DR"`/`"CR"` contains none of them, so the column was never cleaned as numeric on the Python side and never matched as Debit/Credit on the JS side, leaving both blank for every row. Deliberately **not** fixed by loosening the substring match to catch `"dr"`/`"cr"` anywhere in a header — that would false-positive on any header containing those letters as a substring (e.g. `"Address"`, `"Credit Card No"` if such a column existed) and misclassify an unrelated column. Fixed with an **exact-match** tier instead, checked first, before the existing substring-keyword tiers: `keys.find(k => normalizeKey(k) === 'debit' || normalizeKey(k) === 'dr')` (JS) and an `is_bare_dr_cr = col_lower_no_spaces in ('dr', 'cr')` check added to both the `amount_keywords` numeric-cleanup loop and `final_amount_cols` (Python) — exact equality can't accidentally match a longer header, so this adds coverage for the bare-letter case with no false-positive risk for anything else. Verified: 135 rows extracted (up from 0 usable rows — Debit/Credit were previously always blank), with correct per-row Debit-XOR-Credit values matching the raw PDF text (e.g. row 0 `DR: 1000.0, CR: None`; row 1 `DR: None, CR: 220.0`). Regression-checked against Axis/Canara/SBI/UCO/PNB — byte-identical output.
    - **A statement's own trailing summary/total line can be extracted as a fake transaction when the literal word in its date-position cell isn't blank** — a distinct failure mode from the SBI/Axis blank-date summary-row bugs above, which both rely on the marker row's date cell being *empty* to be recognized. The same real Allahabad Bank statement's final table row was `['Total', '', '', '51,220.76', '50,411.00', '']` — pdfplumber's gridline extraction put the literal word `"Total"` exactly where the date normally goes, so the existing blank-date marker filter (`if not clean_row[0] and re.search(...)`) never triggered, since `clean_row[0]` (`"Total"`) is truthy. The row survived as a bogus "transaction" with the statement's actual total DR/CR amounts attached, silently doubling every reported total (confirmed: extracted `totalDR`/`totalCR` were exactly 2× the statement's own printed `"Total 51,220.76 50,411.00"` line — caught via this app's own habit of cross-checking extracted totals against a statement's printed figures, not something the user reported directly). Fixed by widening the condition from "date cell is blank" to "date cell doesn't look like a real date" — reusing the already-existing module-level `_TABLE_DATE_RE` (`row_date_is_real = bool(clean_row[0]) and bool(_TABLE_DATE_RE.match(clean_row[0]))`) — plus adding a bare `\btotal\b` alternative to the marker-phrase regex (word-bounded, so it doesn't false-positive inside `"Subtotal"`, which the existing `sub\s*total` phrase already covers separately). Scoped to this one per-row check inside the "standard style" table loop only — does not touch the narration-based `is_balance_marker_row` DataFrame filter, which has no date guard and would risk matching a legitimate transaction whose narration happens to contain the word "total". Verified: row count dropped from 135 to the correct 134, and `totalDR`/`totalCR` now match the statement's own printed total exactly (`51,220.76`/`50,411.00`, not 2×). Regression-checked against Axis/Canara/SBI/UCO/PNB (via the widened SBI/Axis marker filter, which this shares) — byte-identical output; `font.pdf` (PNB) re-verified unaffected at 42 rows.
    - **`detect_header()` false-positived on a non-transaction "Customer Details / Branch & Account Details" info box, silently emptying the entire result — a distinct, more severe failure mode than any column-mapping bug above (those leave Debit/Credit blank; this dropped every single row).** Root cause chain, confirmed on a real Bank of Maharashtra statement: `detect_header()` used to join a row's (or a 3-row block's) cells into one text blob and substring-search that blob for `≥2` target keywords plus `"date"`.   - **PDF Processing (Chunking Logic):** Mistral API has capacity limits and rejects large PDFs (e.g. 30+ pages) with a `429 Tier Capacity` or `400` error. To solve this, `pdf-lib` is used to split large PDFs into chunks — `PAGES_PER_CHUNK` is a **per-`docType` map**, not a single constant: `BANK_STATEMENT: 1`, `SALES_INVOICE`/`PURCHASE_INVOICE: 20`. Larger chunks mean more content competing for the same per-call output budget, and the Mistral SDK exposes **no** finish-reason/truncation/token-usage signal (confirmed against its response types — `OCRResponse` only has `pages`, `model`, `documentAnnotation`, and a page/byte-count `usageInfo`) telling us if a chunk's JSON annotation was quietly cut short. That failure is invisible — the JSON still parses cleanly, just with fewer rows than the source actually contains — so it can only be prevented, not detected after the fact.
    - `BANK_STATEMENT`'s value chased missing/mismatched-amount reports down through 8 → 5 → 3 → 2, each round reducing but not eliminating the problem, because every one of those sizes still let more than one page share a single OCR call — and multiple pages per call turned out to be the actual unreliable case, at ANY size above one. Direct user-reported comparisons were consistent: a single page reliably reconciles exactly (every entry, every amount); anything with 2+ pages in one call didn't, even well under previously-suspected density ceilings, and even when sent as one large unsplit request instead of several small chunks (tried and reverted — see git history/prior conversation). Set to **1**: every bank statement page gets its own OCR call, unconditionally, regardless of total document length. This means a 40-page statement is 40 separate Mistral calls — more requests, mitigated by `CHUNK_CONCURRENCY` below plus the retry/multi-key infrastructure elsewhere in this file — but it's the only value with direct evidence of being reliably exact, and completeness/correctness has been the explicit priority over speed throughout this whole line of fixes.
    - Bank statements are the risk case (dense multi-line MMT/IMPS/NEFT/UPI narrations pack far more content per page than most documents). This started at 5, was raised to 8 for speed (caused rows to silently go missing on dense statements), reverted to 5 (measurably reduced but on some statements didn't fully eliminate the loss — a density-dependent content-budget issue, not a hard page-count cliff), and is now **3** — a deliberate trade favoring completeness over speed, since no fixed page count is *provably* safe for unboundedly dense narrations. Paired with a prompt change (`bankStatementPrompt` in `schemas.ts`) explicitly instructing the model not to stop extracting upon hitting a summary/closing-balance line, especially on the final page, and a diagnostic-only cross-check (`warnIfRowCountLooksShort()`) that counts date-led lines in each chunk's raw OCR markdown (`ocrResponse.pages[].markdown`, returned alongside the structured JSON at no extra cost) and logs a warning if the actual row count looks suspiciously low against that estimate — heuristic, not always accurate, but real signal from the same API call.
    - **Zero-transaction chunks get one retry, not just a log line (bank statements only):** a chunk whose annotation comes back with rows.length === 0 is ambiguous on its own — could be a genuinely blank divider page, or the same silent-truncation failure the paragraph above describes. Reusing the same date-led-line count as `warnIfRowCountLooksShort()`, if the chunk's raw markdown shows ≥1 date-led line, that's real evidence this page has content the structured extraction just missed — worth one fresh retry (a brand-new OCR call, not a re-read of the same response) before accepting an empty result. If the retry also comes back empty, it's accepted as genuinely blank. Confirmed necessary against a real multi-page statement where a page with 3 real transactions came back with zero on the first attempt, silently dropping all 3 — previously only logged as a warning, never corrected. Bounded to exactly one retry per chunk, only under this narrow condition, so it can't loop or add cost to chunks that already succeeded.
    - **Watch out:** the first version of that "don't stop early" prompt wording was too strong ("the transactions array MUST have N entries, do not omit any row for any reason") and caused a *different* regression — the model started treating "Page Total"/closing-balance summary lines as if they were transactions to avoid seeming to "omit" a row, inflating totals even though row *count* looked complete. `bankStatementPrompt` now explicitly separates two rules: (1) never stop extracting because of a summary line, but (2) never let a summary line itself become a transaction entry or contribute its amount to any Debit/Credit field. If total amounts stop matching again after a prompt change here, check for this exact failure mode first.
    - Invoices are the opposite case — real invoices are essentially always 1-2 pages, so 20 means `splitPdf()`'s `totalPages <= pagesPerChunk` short-circuit almost always applies and they're never actually split, while still capping well under the ~30-page capacity threshold for the rare unusually-long itemized invoice.
  - **Encrypted/permission-restricted PDFs:** loaded with `{ ignoreEncryption: true }` so pdf-lib doesn't refuse to open bank-issued PDFs that are flagged encrypted purely for owner-password restrictions (block printing/editing, no password needed to open). That flag only bypasses pdf-lib's load-time exception — it does **not** decrypt content streams (pdf-lib has no decryption support at all). So if such a PDF needs to be split (`pdfDoc.isEncrypted && totalPages > PAGES_PER_CHUNK`), `copyPages()`/`save()` would silently copy still-encrypted stream bytes into an unencrypted wrapper and corrupt every chunk. `splitPdf()` detects this and sends the original file to Mistral as a single unsplit request instead, letting Mistral's own backend handle standard PDF decryption directly (the same way any PDF reader would) — this only risks hitting Mistral's own capacity limit for unusually large (~30+ page) encrypted documents, which surfaces as a normal, already-handled retryable error rather than silent corruption.
  - **Upload & Signed URLs:** Because of Next.js fetch polyfill bugs with `FormData`, files are uploaded using native `fetch` to Mistral's file API to get a signed URL.
  - **No page-count limit:** a PDF splits into as many `PAGES_PER_CHUNK[docType]`-page chunks as it needs — for bank statements, that's one chunk per page, always. `CHUNK_CONCURRENCY` (default 3) bounds how many chunks of a *single* document are OCR'd in parallel via a local `p-queue`, so a large bank statement doesn't take as long as its page count times a single call would. Results are collected into an index-preserving array so merged rows stay in original page order regardless of which chunk's OCR call finishes first. This stacks with `ocrQueue`'s concurrency (`src/lib/queue.ts`), which caps how many *documents* run at once. If a bank-statement chunk's parsed annotation comes back with zero transactions, or with a row count well under what `warnIfRowCountLooksShort()`'s markdown-based estimate expects, a warning is logged (not necessarily a bug — could be a genuinely blank divider page — but useful to correlate against if row counts look short).
  - **Multi-API-key load balancing (`MistralKeyPool`):** Mistral's capacity limits are per API key/account tier. If `MISTRAL_API_KEYS` (comma-separated) is set, every OCR call — per chunk, not per document — is routed through whichever configured key currently has the fewest requests in flight ("least connections"). With only `MISTRAL_API_KEY` (single key) set, this collapses to exactly the old single-client behavior; nothing changes for that setup. On a `429`, the failing key is excluded for that chunk's remaining retry attempts (so the retry goes to a different, non-constrained key) and the normal exponential backoff wait is skipped entirely via `err.fastRetryHintMs` — there's nothing to wait out on a key that wasn't the one that hit the limit. `hasMistralApiKey()` / `getMistralKeyCount()` are exported for route validation and diagnostics.
  - **Retries:** Each chunk's upload + OCR call is wrapped in `withRetry()`, which retries transient failures — HTTP 429/500/502/503/504, network errors (connection reset/timeout), and Mistral's "File could not be fetched" / error code `3310` (an Azure Blob read-after-write propagation race right after upload) — with **exponential backoff + jitter** (up to 5 attempts, capped at 20s per wait, honoring a `Retry-After` header if sent, or the key-switch fast-retry hint above if that applies). Retry eligibility is based on the typed `statusCode` the Mistral SDK attaches to errors, not string-matching. Non-retryable errors (bad auth, bad schema) fail immediately. Every route sets `maxDuration = 800` to give large multi-chunk extractions room to finish (some hosts, e.g. Vercel Hobby, hard-cap duration regardless of this setting).
  - **A single chunk permanently exhausting all 5 retries no longer fails the whole document.** Previously, every chunk's task lived inside one `Promise.all()`, so if even one chunk's `withRetry()` gave up (confirmed in production: a sustained burst of Mistral-side `502 "An invalid response was received from the upstream server"` — infrastructure trouble on Mistral's end, not this app), the whole `Promise.all` rejected and the document failed outright — discarding every OTHER chunk that had already succeeded (on a 20-page statement, losing 19 good pages' worth of already-paid-for OCR calls because ONE page hit bad luck) and forcing the caller to re-run the entire slow extraction from scratch. Each chunk's task now catches its own permanent failure internally instead of rethrowing, recording `{ chunk, totalChunks, error }` into an `incompleteChunks` array; the merge step treats an unset `chunkResults[index]` (a failed chunk never assigns its slot) as `[]` rather than crashing on `...undefined`. `runOcr()`'s return type (`RunOcrResult`) gains an optional `incompleteChunks` field, present only when non-empty. This is deliberately **never silent**: `extractHandler.ts` still returns `success: true`/`200` (most of the document usually did extract correctly, and that data is real and usable) but adds a top-level `warning` string plus the `incompleteChunks` array to the response — a caller that only checks `success` won't miss it, since the field's presence is the signal, not its content. The whole-file `ocrCache` write is also skipped whenever `incompleteChunks` is present, specifically so a caller's retry (re-uploading the same file hoping the flaky page succeeds this time) triggers a fresh attempt at the missing page(s) instead of being served the same incomplete cached result forever.

Rare in practice; if it recurs, check `data/ledger-memory.json` for outlier entries.
  - **Merging:** the `transactions` arrays from all chunks are merged in original order.
  - **Brought-Forward/balance-marker row filter (`filterBroughtForwardRows()`, bank statements only, both engines):** RULE 2 in `schemas.ts` already tells the model to exclude "Balance B/F"/"Brought Forward"/opening/closing-balance rows from `transactions`, but that's a prompt instruction, not a guarantee — this is a deterministic regex safety net for when it doesn't comply, mirroring the same filtering `parse_bank_statement.py` already applies to its own output (`is_bf_row`/`is_balance_marker_row` there). Confirmed necessary against a real extraction: a `"BROUGHT FORWARD"` opening-balance line came back as its own transaction row, with the *wrong* balance value attached (the next real transaction's balance, not its own — `0.00` on the source statement). Applied to Mistral-sourced rows (where it fixes a real bug) and Python-sourced rows (redundant there since the script already strips these, but kept for consistency between both paths).
  - **Ambiguous Debit-vs-Credit resolution (`resolveAmbiguousDebitCreditRows()`, bank statements only, both engines):** a real transaction has exactly one of Debit/Credit populated — a row with both (a table/OCR column misalignment on the Python side, or the model getting confused despite RULE 1) is resolved using that row's own `Balance` field as a tiebreaker: the running balance can only have moved by adding Credit OR subtracting Debit from the *previous* row's balance, so whichever operation actually reproduces this row's stated balance (within 1 paisa) is kept; the other is discarded. Only ever acts when it can prove which value is right — if neither operation matches, or there's no usable previous/current balance to check against (e.g. the very first row), the row is left untouched rather than guessed at. Runs right after `filterBroughtForwardRows()` and before `dedupeBankStatementRows()` for both engines, so downstream dedup/reconciliation see the corrected values. Verified against a real example (`Debit: 30038, Credit: 55`, previous balance `5963332.16` → current balance `5963387.16`): only the `+55` operation reproduces the stated balance, so `Credit: 55` is kept and the spurious `Debit: 30038` is cleared.
  - **Deduplication (`dedupeBankStatementRows()`, bank statements only):** removes exact-duplicate rows (same DATE, DESCRIPTION, CHEQUE_NO, Debit, Credit) — a guard against the same transaction being reported by two adjacent chunks when it visually sits near a chunk's page boundary. **Only compares each row against the last `DEDUP_WINDOW` (3) already-kept rows, not the whole document.** The first version compared globally, which was itself a bug: a large statement is far more likely to contain a genuinely recurring transaction (the same bank fee, the same recurring UPI payment) sharing an identical date/description/amount purely by coincidence, and a global check silently deleted that second legitimate occurrence — this was a real, confirmed contributor to "small statements reconcile exactly, large ones come up short." A true chunk-boundary duplicate always lands immediately adjacent to its twin in the merged sequence, so a small window catches the real failure mode without the false-positive risk.
  - **Balance reconciliation (bank statements only):** the schema also asks for `openingBalance`/`closingBalance` on each chunk (empty string when a chunk's pages don't show them — most won't). Merged as: first non-empty `openingBalance` in page order, last non-empty `closingBalance` in page order (handles statements that print a running per-page balance in addition to the true statement-level opening/closing balance). `reconcileBankStatement()` sums the extracted Debit/Credit columns and compares `closingBalance - openingBalance` against `totalCredit - totalDebit` (0.5 rupee tolerance for rounding) — this is the actual "does the AI's output match the bank's own numbers" check, done automatically rather than left to the model's judgment. Returned as `bankSummary` on `RunOcrResult`, threaded through `extractHandler.ts` into the API response, and surfaced in `ResultsTable.tsx` as a totals bar + match/mismatch badge. `reconciled` is `null` (not `false`) when the statement didn't show both balances clearly enough to check — a missing check is reported differently from a failed one.
- **`src/lib/ledgerMemory.ts`**: Persistent, rules-based "learning" for ledger names — **not** model fine-tuning (see the note below on why that's not possible here). Every party name `ledger.ts` confidently derives is recorded to `data/ledger-memory.json` (`party name → ledger name`). On the next transaction, `lookup()` checks whether any previously-learned party name appears anywhere in the new description *before* re-running the parsers — so a narration format the parsers can't handle can still resolve correctly if it mentions a party we've already seen, and repeats resolve without re-deriving them. This is what actually delivers "gets more accurate the more statements you process." Keys shorter than 4 characters are ignored to avoid false-positive substring matches.
- **`src/lib/ocrCache.ts`**: Exact-duplicate-content result cache, at two granularities:
  - **Whole-file** (`getCached`/`setCached`): hashes the uploaded file's bytes (SHA-256); if that exact file was already processed for the same `docType`, `extractHandler.ts` returns the stored result instantly before ever enqueueing.
  - **Per-chunk** (`getCachedChunk`/`setCachedChunk`, under `data/ocr-cache/chunks/`): inside `runOcr()`'s chunk loop, each `PAGES_PER_CHUNK` slice is hashed and checked independently — a chunk byte-identical to one already processed (even from a *different* original file: a corrected re-export, overlapping date-range exports, a resubmission after a network failure) skips Mistral for that chunk while genuinely new chunks in the same document still go through normally.
  - Both are safe because they're keyed by exact content hash: a hit only ever happens for bytes already read before, so there's no risk of returning stale data for content that's actually new. **This explicitly does NOT extend to "recognize this bank's layout and skip re-reading a new statement"** — a new statement's transactions have never been read before regardless of how many prior statements from that bank were processed, and skipping real OCR for them would mean either returning wrong/stale data or attempting to reimplement OCR via template-matching, neither of which is sound. See the note in `runOcr()`'s chunk loop for the exact reasoning.
  - Complements `ledgerMemory` (which helps *new* documents that share a *counterparty*, not a whole chunk's content, with previously-seen ones).
  - Both cache layers also store an optional `meta: Record<string, string>` alongside `rows` (`CachedResult`/`CacheEntry`) — used to persist bank-statement `openingBalance`/`closingBalance` per chunk and the full `bankSummary` (JSON-stringified) for whole-file hits, so a cache hit doesn't lose reconciliation data. `meta` is entirely optional and omitted for invoices — fully backward compatible with cache entries written before this existed.
- **`src/lib/queue.ts`**: Implements `p-queue` with a concurrency limit of 4 to throttle active OCR tasks. `MAX_QUEUE_SIZE` (env `OCR_MAX_QUEUE_SIZE`, default 20) bounds how many tasks (running + waiting) are held at once — each holds an uploaded file in memory, so an unbounded queue under heavy concurrent load risks exhausting server memory. `enqueueOcr()` throws `QueueSaturatedError` immediately when saturated, which `extractHandler.ts` maps to an HTTP `503` with `Retry-After` rather than accepting and queueing the request anyway.
- **`src/lib/schemas.ts`**: Defines the strict JSON schemas and custom system prompts for `BANK_STATEMENT`, `SALES_INVOICE`, and `PURCHASE_INVOICE`. This enforces the Mistral model to return data in the exact structured format expected by the frontend table.
  - **Bank Statement Prompt** is extensively detailed with 7 explicit rules:
    - **RULE 1:** Extract all real transactions (dated, narration, single Debit XOR Credit).
    - **RULE 2:** Never include Opening Balance/B/F, Closing Balance/C/F, Page Total, or Sub Total rows.
    - **RULE 3:** Completely ignore the running Balance column — its values must never enter Debit or Credit.
    - **RULE 4:** Preserve decimal points exactly as printed; strip ₹/commas only.
    - **RULE 5:** Only report openingBalance on the first page, closingBalance on the last; leave empty otherwise.
    - **RULE 6:** Date must be DD/MM/YYYY.
    - **RULE 7:** Suggest a Tally ledger name.
- **`src/lib/extractHandler.ts`**: Shared request handler behind all three `/api/extract*` routes — see section 2 above. Also owns the `ocrCache` check/store around `enqueueOcr()`.

**On "training"/fine-tuning for speed:** Mistral's OCR endpoint is a stateless hosted model called over HTTPS — it does not learn from prior requests, and there's no fine-tuning path exposed for the structured-annotation OCR endpoint this app uses. No code running in this app can change that, and — importantly — that's true regardless of how many statements from the same bank have been processed before: a new statement's actual transactions have never been read before and must go through real OCR every time, no matter how familiar the layout is. "Recognize this bank's format and skip re-reading a new document" is NOT something this app does or should do — it would mean returning stale/wrong data for content that was never actually read. What DOES genuinely improve with usage, safely: `ledgerMemory.ts` (rules-based memory of confirmed party→ledger mappings, growing with every statement processed) and `ocrCache.ts` (instant results for exact-duplicate files AND exact-duplicate page-chunks, even across different original files) — both are real "gets better/faster over time" mechanisms because they only ever reuse output for byte-identical input they've already read, never for genuinely new content. Everything else (`PAGES_PER_CHUNK`/`CHUNK_CONCURRENCY` tuning, multi-key load balancing, prompt/schema precision) is a one-time architectural choice, not something that improves further just from more usage.
**Data persistence caveat:** `ledgerMemory.ts` and `ocrCache.ts` write to `data/` on disk (gitignored). This only accumulates meaningfully on a persistent server process — confirmed that's this app's deployment model. On a serverless platform where instances are short-lived/ephemeral, this would degrade to per-invocation memory only; an external store (Redis/Postgres) would be needed instead.

## 🌐 External API Usage

These endpoints are usable directly by any external client (not just this repo's frontend) once deployed — send `multipart/form-data`, get JSON back.

| Endpoint | `docType` field | Notes |
|---|---|---|
| `POST /api/extract` | required: `BANK_STATEMENT` \| `SALES_INVOICE` \| `PURCHASE_INVOICE` | generic — same one the web UI uses |
| `POST /api/extract/bank-statement` | not sent (implied) | dedicated bank statement endpoint |
| `POST /api/extract/invoice` | required: `SALES_INVOICE` \| `PURCHASE_INVOICE` | dedicated invoice endpoint, both directions |

**Request:** `multipart/form-data` with a `file` field (PDF or image; PDF up to 200MB, images up to 25MB) and `docType` where applicable.

**Success response** (`200`):
```json
{
  "success": true,
  "docType": "BANK_STATEMENT",
  "rowCount": 42,
  "columns": ["DATE", "DESCRIPTION", "CHEQUE_NO", "Debit", "Credit", "LEDGER"],
  "data": [ { "DATE": "01/04/2024", "...": "..." } ],
  "processingTimeMs": 18342,
  "cached": false,
  "bankSummary": {
    "totalDebit": "12345.00",
    "totalCredit": "9800.50",
    "openingBalance": "21334.39",
    "closingBalance": "18789.89",
    "actualNetChange": "-2544.50",
    "expectedNetChange": "-2544.50",
    "reconciled": true
  }
}
```
`cached: true` means this exact file (by content hash) was already processed for this `docType` before, and the result was returned instantly from `ocrCache` without calling Mistral again.

`bankSummary` is only present for `BANK_STATEMENT`. `totalDebit`/`totalCredit` are always computed from the extracted rows. `openingBalance`/`closingBalance` are the statement's own printed figures, when visible in the document. `reconciled` is `true`/`false` only when both balances were found and compared against the extracted totals (0.5 rupee tolerance); it's `null` when the statement didn't show both balances clearly enough to check — `null` means "not verified," not "verified and wrong." On a mismatch (`reconciled: false`), `discrepancy` gives the difference and `expectedNetChange`/`actualNetChange` show what the statement implies vs. what the extracted rows imply.

**Error response** (`400` validation / `500` server / `503` overloaded):
```json
{ "success": false, "error": "human-readable message" }
```
A `503` includes a `Retry-After` header — back off and retry rather than hammering the endpoint.

**Scaling for concurrent users:**
- `OCR_QUEUE_CONCURRENCY` (env, default 4) — max **documents** processing in true parallel at once (each a full extraction: the local Python parse attempt for a bank statement, or the whole Mistral chunked-OCR pipeline for anything else). Previously a hardcoded constant in `queue.ts` — made configurable so throughput can be tuned to a given server's actual CPU/memory headroom without a code change. Each concurrent slot can spawn a Python subprocess and/or hold an uploaded file in memory, so this is a real resource dial — raise it gradually and watch server memory/CPU on a shared or memory-constrained host, rather than jumping straight to a high number.
- `OCR_MAX_QUEUE_SIZE` (env, default 20) — max requests held (running + waiting) before new ones get a `503`. Raise if you have the memory headroom for more concurrently-buffered files; lower if the process is memory-constrained.
- `MISTRAL_API_KEYS` (env, comma-separated) — set this instead of a single `MISTRAL_API_KEY` to load-balance OCR calls across multiple Mistral keys, directly increasing effective throughput and reducing 429 "capacity exceeded" errors under concurrent load. Falls back to `MISTRAL_API_KEY` (single key) if unset — no behavior change for existing single-key deployments.
- True horizontal scaling (running multiple instances of this app behind a load balancer/reverse proxy) is a deployment-platform concern, not application code — e.g. multiple container replicas behind an nginx/ALB/Vercel-style router. The in-process concurrency controls above (queue depth, chunk concurrency, key pool) apply independently within each instance.

## 🔄 Data Flow (End-to-End)

1. **User Action:** User drags and drops a PDF into `UploadForm` and clicks "Extract Data".
2. **Frontend State:** `page.tsx` sets `loading = true`, starts the live stopwatch timer, and sends a `FormData` POST request to `/api/extract` (the web UI always uses the generic route; external API consumers can use `/api/extract/bank-statement` or `/api/extract/invoice` instead).
3. **Validation:** `extractHandler.ts` validates the request (file present, docType allowed, MIME type, size).
4. **Cache check:** the file's content is hashed (SHA-256); if this exact file was already processed for this `docType` (`ocrCache`), the stored result is returned immediately — skipping everything below.
5. **Queueing:** on a cache miss, the task is pushed into `p-queue` via `enqueueOcr()`. If the queue is already at `MAX_QUEUE_SIZE`, the request is rejected immediately with `503` instead of being queued.
6. **PDF Chunking:** `mistral.ts` intercepts the PDF, reads it into memory, and splits it into `PAGES_PER_CHUNK[docType]`-page chunks using `pdf-lib` (1 page per chunk for bank statements — every page is its own OCR call — 20 for invoices — see the chunking-logic note above for why these differ).
7. **OCR Extraction:** For each chunk, run with up to `CHUNK_CONCURRENCY` chunks in flight at once:
   - Hash this chunk's bytes and check the per-chunk cache (`ocrCache.getCachedChunk`) — a chunk byte-identical to one already processed (from this document or a different one) skips straight to its cached rows, no Mistral call at all.
   - On a chunk-cache miss: acquire the least-busy configured Mistral API key from the pool (see `MistralKeyPool` above — a no-op if only one key is configured).
   - Upload chunk via native `fetch` -> get `signedUrl`.
   - Call `ocr.process` with the `signedUrl` and the strict JSON schema/prompt.
   - If either step fails with a transient error (429/500/502/503/504, a network error, or the file-propagation race), retry with exponential backoff + jitter (up to 5 attempts) — or, for a 429 with more than one key configured, immediately retry on a different key instead of waiting.
   - On success, store the chunk's rows in the per-chunk cache for future reuse.
8. **Post-processing:** Amounts are normalized (`normalizeAmount()`). For bank statements: exact-duplicate rows are removed (`dedupeBankStatementRows()`), `LEDGER` is re-derived deterministically from the narration (`suggestBankLedger()`, checking `ledgerMemory` first and recording new results into it), and the extracted totals are cross-checked against the statement's own opening/closing balance (`reconcileBankStatement()`) to produce `bankSummary`.
9. **Merging:** All extracted arrays are concatenated into a single master array, in original page order.
10. **Cache store:** the result is saved into `ocrCache` keyed by this file's content hash, so re-processing the identical file later is instant.
11. **Response:** The API responds with `{ success, docType, rowCount, columns, data, processingTimeMs, cached }`, plus `bankSummary` for bank statements.
12. **UI Shift:** `page.tsx` receives the data, stops the timer, and switches the UI to the side-by-side view. The native browser PDF preview loads on the left, and the `ResultsTable` renders the data (including total parse time, and — for bank statements — a totals bar with Total Debit/Total Credit and a match/mismatch badge against the statement's own balance) on the right.
